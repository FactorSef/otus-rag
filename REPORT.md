## Процесс разработки *(текст ИИ)*

Работа шла короткими шагами «предложение → решение автора → реализация → тесты → коммит». Код без согласованного плана не писался.

   - база двуязычная → модель эмбеддингов `multilingual-e5-large`.

## Подход к разбивке на чанки *(текст ИИ)*

Стратегия выбирается по типу файла (подробно — `ARCHITECTURE.md`, раздел 4.1):

- **Markdown** — по заголовкам h1–h3, крупные разделы дорезаются рекурсивно. Цепочка заголовков сохраняется в метаданных.
- **Код** (`.py/.js/.ts`) — `RecursiveCharacterTextSplitter.from_language`: режет по границам функций и классов.
- **JSON / YAML** — по ключам; путь ключей становится разделом.
- **Текст** — рекурсивно по абзацам, строкам и предложениям.

У каждого чанка есть источник, номера строк и раздел, поэтому ответ ссылается на конкретное место в файле. Размер чанка 800 символов при перекрытии 120 подобран под лимит e5 в 512 токенов.

## Ключевые проблемы и решения *(текст ИИ, дополнение к записям автора)*

- **Таймауты MCP‑клиентов при индексации.** Индексация 695 КБ на CPU занимает ~12 минут, а MCP Inspector по умолчанию ждёт 10 с. Решение — фоновая индексация с прогрессом в `index_status`.
- **Рассуждения qwen3.** Без `/no_think` оценка одного чанка занимала ~200 токенов и ~4 с, с ним — ~10 токенов. Добавлены параметр `LLM_PROMPT_SUFFIX` и вырезание блоков `<think>`.
- **Системный прокси Windows.** Python‑клиенты (httpx) отправляли запросы к `localhost` через VPN‑прокси и получали 503. Решение — `NO_PROXY=localhost,127.0.0.1`, описано в README.
- **Ошибка, найденная тестом.** Тест «сбой посреди индексации» показал, что после сбоя следующий запуск принимал ситуацию за смену модели и стирал всё проиндексированное. Исправлено до того, как проблема проявилась бы на реальных данных.
- **Code review.** Нашлись гонка при пересоздании коллекции Chroma, выход glob за пределы папки, блокировка event loop и «пустые» повторы графа. Всё исправлено, на каждую проблему есть тест.

## Удачные и неудачные промпты *(текст ИИ)*

**1. Неудачный промпт к ИИ — и удачная поправка автора.** Для перевода вики ИИ сначала пошёл в обход: стал замерять скорость перевода локальной моделью в LM Studio, и запрос завис по таймауту. Автор прервал: *«А зачем ты используешь lmstudio когда ты сам можешь перевести?»*

*Разбор:* исходная задача «переведи на русский» не уточняла исполнителя, и агент выбрал более сложный путь через локальную модель. Перевод силами самого Claude оказался быстрее и качественнее. Вывод: если в задаче важен способ выполнения, его стоит указывать явно.

**2. Удачный промпт для модели графа — `/no_think`.** qwen3 по умолчанию «рассуждает» перед ответом. Для оценки релевантности это лишнее: ответ — одно слово в JSON. Суффикс `/no_think` в каждом запросе сократил ответ с ~200 до ~10 токенов, а качество оценки не упало.

**3. Неудачный промпт графа — переформулировка на другой язык.** На вопрос *«What is the name of the lab's mascot?»* (факт записан только по‑русски) qwen3‑4b выдал русский запрос *«Какой является мascot лаборатории?»* — смесь алфавитов, которая не находит нужный документ. Тот же вопрос по‑русски отвечается верно.

*Разбор:* 4B‑модели не хватает для надёжного перевода терминов. Варианты улучшения:
- модель крупнее;
- явный пример перевода в промпте (few‑shot);
- поиск по исходному вопросу с большим весом векторной части: мультиязычные эмбеддинги сами сопоставляют «mascot» и «талисман».

**4. Удачный приём — сначала план, потом код.** Запрос *«Давай распланируем архитектуру решения»* до написания кода выявил развилки (внешняя LLM, языки, корпус) до реализации. Ни одно решение потом не пришлось переделывать.
