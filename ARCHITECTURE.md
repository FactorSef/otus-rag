# Архитектура RAG Knowledge Base

MCP‑сервер, превращающий папку с документами в поисковую базу знаний. Внутри — Corrective RAG на LangGraph, гибридный поиск (BM25 + вектор → RRF) и внешняя LLM, адрес которой передаётся через конфиг.

## 1. Компоненты

│  .vscode/mcp.json → http://localhost:8000/mcp                          │
└───────────────────────────────┬────────────────────────────────────────┘
                                │ MCP, streamable HTTP
┌───────────────────────────────▼────────────────────────────────────────┐

│      ▼                               ▼          └─ broaden┘            │

## 2. Развёртывание

| Сервис (`docker-compose.yml`) | Профиль | Назначение |
|---|---|---|
| `rag-server` | всегда | MCP‑сервер на `:8000/mcp`, `/health` для healthcheck. Тома: `./sample_docs → /app/sample_docs` (ro), `${DOCS_DIR} → /app/docs` (ro), `rag-data → /data` (индекс Chroma и состояние). `extra_hosts: host.docker.internal:host-gateway` — доступ к LLM на хосте и в Linux. |
| `ollama` | `local-llm` | Ollama, модели в томе `ollama-models`. |
| `ollama-init` | `local-llm` | Одноразовый `ollama pull ${LLM_MODEL}`; `rag-server` ждёт его завершения (`depends_on … required: false` — без профиля зависимость игнорируется). |

- `docker compose up --build` — только сервер; LLM внешняя (`LLM_BASE_URL`, по умолчанию `http://host.docker.internal:11434`).
- `LLM_BASE_URL=http://ollama:11434 docker compose --profile local-llm up --build` — дополнительно Ollama со скачанной моделью.
- `.env` необязателен (`env_file … required: false`): без него работают значения по умолчанию.
- Рабочая директория контейнера — `/app`, поэтому `index_folder("./sample_docs")` работает буквально; свои документы — через `DOCS_DIR` и `index_folder("./docs")`.

**Образ** (`Dockerfile`, multi‑stage):

1. `build` — `uv sync --frozen --no-dev` в `/opt/venv` (слой зависимостей кэшируется до изменения `uv.lock`).
2. `models` — модель эмбеддингов скачивается **при сборке** (`PRELOAD_EMBEDDINGS=1`, ~2,2 ГБ для e5‑large). В рантайме `HF_HUB_OFFLINE=1`: первый запуск не зависит от сети, индексация и поиск работают без LLM. Для `EMBEDDING_PROVIDER=ollama|openai|chroma` — `PRELOAD_EMBEDDINGS=0`.
3. `runtime` — `python:3.12-slim`, непривилегированный пользователь `app`, `HEALTHCHECK` по `/health`.

Сервер стартует, даже если LLM недоступна: проверка выполняется при старте (предупреждение в логе), в `index_status` и при вызове `ask_question` (понятная ошибка с адресом и именем модели).

**CI** (`.github/workflows/ci.yml`, GitHub Actions, на push в `main` и на pull request):

1. `lint-test` — `uv sync --frozen`, `ruff check`, `ruff format --check`, `pytest` (без сети и моделей: заглушки эмбеддингов и LLM).
2. `docker` — после успешных тестов: сборка образа с `PRELOAD_EMBEDDINGS=0` (модель на 2 ГБ в CI не нужна), запуск контейнера и smoke‑тест `GET /health`.

## 4. Индексация

### 4.1. Разбиение на чанки

Стратегия выбирается по расширению: смысловая единица у текста и кода разная.

| Тип | Стратегия | Зачем |
|---|---|---|
| `.md` | Собственное разбиение по заголовкам h1–h3 (заголовки внутри ``` игнорируются) → крупные разделы дорезаются `RecursiveCharacterTextSplitter.from_language(MARKDOWN)` | Раздел вики — естественная единица смысла. Свой сплиттер вместо `MarkdownHeaderTextSplitter`: тот нормализует пробелы в строках, и позиции чанков в исходном файле теряются. Разделы из одного заголовка без текста пропускаются. |
| `.txt` | `RecursiveCharacterTextSplitter` (абзац → строка → предложение) | Нет структуры, режем по естественным границам. |
| `.py` `.js` `.ts` | `RecursiveCharacterTextSplitter.from_language(...)` | Режет по границам классов/функций; функция целиком лучше отвечает на вопрос «где/как используется X». |
| `.json` | `RecursiveJsonSplitter` (списки → словари с индексами) | Чанк — валидный JSON‑фрагмент поддерева, `section` — путь ключей. Фрагмент сериализуется заново, поэтому диапазон строк приблизительный: от строки первого ключа до начала следующего чанка. |
| `.yaml` | Разбиение по ключам верхнего уровня, крупные блоки дорезаются рекурсивно | Текст YAML остаётся исходным (с комментариями), строки точные. Невалидный YAML/JSON индексируется как текст. |

Метаданные каждого чанка: `source`, `file_type`, `chunk_index`, `start_line`, `end_line` (1‑based, включительно), `section` (цепочка заголовков `h1 > h2` / путь ключей), `file_hash`.

`source` — путь относительно рабочей директории сервера (`sample_docs/wiki/a8.md`), для файлов вне её — абсолютный. Так файлы из разных индексированных папок не конфликтуют.

Для эмбеддинга и BM25 используется не только текст чанка, но и строка контекста `source | section` (`search_text()`): заголовок раздела и имя файла часто несут ключевые слова, которых нет в самом фрагменте. Пользователю возвращается исходный текст.

### 4.2. Идемпотентность и инкрементальность

- `id = sha1(source + ":" + chunk_index)`.
- У каждого файла хранится `file_hash` (sha1 содержимого). Неизменённые файлы при повторной индексации пропускаются — это важно для тяжёлой e5‑large на CPU.
- Чанки изменённых файлов удаляются перед upsert (`where={"source": {"$in": ...}}`) — нет дублей, корректно обрабатываются укоротившиеся файлы.
- Файлы, исчезнувшие с диска внутри индексируемой папки, удаляются из индекса.
- Статистика (`last_indexed_at`, `embedding_id`, проиндексированные папки, файлы по типам, отчёт последнего запуска) хранится в `index_state.json` рядом с Chroma и переживает рестарт; количество файлов и чанков считается по самой коллекции.
- Если `embedding_id` (`провайдер:модель`) в состоянии не совпадает с конфигом — `index_status` предупреждает, `index_folder` пересоздаёт коллекцию (векторы разных моделей несовместимы). До пересборки поиск отвечает понятной ошибкой, а не результатами из чужого векторного пространства.
- `chunking_id` (версия сплиттера, `CHUNK_SIZE`, `CHUNK_OVERLAP`) хранится там же: при его смене все файлы переразбиваются без сброса коллекции, иначе в индексе смешались бы чанки разных размеров.
- Файлы, из которых не получилось ни одного чанка (например, `{}`), запоминаются по хешу в `empty_files` и не обрабатываются заново при каждом запуске.
- Glob проверяется: абсолютные шаблоны и `..` запрещены — индексация не выходит за пределы указанной папки.

- Файл считается проиндексированным, только если в коллекции есть все его чанки (`file_chunks` в метаданных). Прерванная индексация (ошибка, рестарт контейнера) не оставляет «полуфайлов», которые следующий запуск ошибочно пропустил бы: недописанные файлы переиндексируются, дописанные — сохраняются.

### 4.3. Фоновая индексация

e5‑large на CPU тратит ~0,4 с на чанк: корпус в 500–700 КБ (~1200 чанков) индексируется 8–10 минут, а MCP‑клиенты ждут ответа инструмента секунды (MCP Inspector — 10 с по умолчанию). Поэтому индексация разделена на две фазы:

| Фаза | Где выполняется | Что делает |
|---|---|---|
| `Indexer.plan()` | синхронно, в вызове инструмента | проверка пути, сканирование, чанкинг, сравнение хешей; ошибки входа (нет папки, нет подходящих файлов) возвращаются сразу |
| `Indexer.apply()` | фоновый поток (`JobRunner`) | эмбеддинги батчами, запись в Chroma, сохранение состояния; по завершении — перестройка BM25 |

- `index_folder` ждёт завершения до `INDEX_WAIT_S` секунд (5 по умолчанию): маленькая папка или повторная индексация без изменений возвращают итоговый отчёт сразу, большая — `state: running` и подсказку следить через `index_status`.
- `index_status` показывает задачу: `state` (`running` / `completed` / `failed`), `chunks_done / chunks_total`, `percent`, `eta_s`, ошибку или итоговый отчёт.
- Одновременно выполняется одна задача; повторный вызов во время работы возвращает понятную ошибку.
- `ChromaStore` потокобезопасен: все обращения к коллекции идут под одной блокировкой, поэтому пересоздание коллекции фоновой задачей не попадает на середину запроса поиска. Счётчик `generation` растёт при сбросе, и BM25 перестраивается при следующем поиске, чтобы не возвращать стёртые чанки.
- Планирование (обход папки, чтение и чанкинг) тоже выполняется вне event loop (`asyncio.to_thread`): пока оно идёт, сервер отвечает на другие запросы.
- Пока задача идёт, поиск работает по уже проиндексированным данным; задача становится `completed` только после перестройки BM25.
- Если индекс ещё пуст (первая индексация после запуска), `ask_question` и `find_relevant_docs` возвращают ошибку с прогрессом и оставшимся временем. Когда часть чанков уже записана, они отвечают по частичному индексу, но первым полем ответа идёт `warning` («индекс готов на 37%, ответ может быть неполным, в том числе „не найдено“») — иначе агент получил бы уверенное „в базе этого нет“ посреди индексации — хост‑агент может передать его пользователю, а не считать сервер сломанным. В README этому посвящена отдельная сноска: индексацию демо‑базы нужно запускать сразу после старта, до вопросов агенту.

### 4.4. Эмбеддинги

По умолчанию — `intfloat/multilingual-e5-large` через fastembed (ONNX, без torch), 1024 измерения, RU+EN в одном пространстве: русский вопрос находит английский чанк и наоборот.

Особенность e5: модель обучена с префиксами — при индексации текст отправляется как `passage: …`, запрос как `query: …`. Префиксы добавляет обёртка в `embeddings.py`, остальной код о них не знает. Ограничение длины — 512 токенов, что покрывает чанк в 800 символов с запасом.

## 5. Гибридный поиск

- **BM25** (`rank_bm25.BM25Okapi`, собственный `BaseRetriever` — `langchain-community` объявлен устаревшим) — точное совпадение слов. Токенизатор: нижний регистр, `\w+` с поддержкой кириллицы, стемминг Snowball (русский или английский — по алфавиту слова: «принтера» → «принтер»), идентификаторы сохраняются целиком и дополнительно разбиваются на части (`TOKEN_EXPIRY_HOURS` → `token_expiry_hours`, `token`, `expiri`, `hour`; `maxFeedRate` → `maxfeedrate`, `max`, `feed`, `rate`).
- **Вектор** — косинусная близость в Chroma.
- **RRF** — `EnsembleRetriever`: `score(d) = Σ wᵢ / (60 + rankᵢ(d))`. Документ, высоко стоящий в обоих списках, побеждает документ, найденный только одним методом.
- BM25 живёт в памяти и перестраивается из содержимого Chroma при старте и после каждой индексации — источник истины один.

`find_relevant_docs` вызывает только этот слой (без LLM).

## 6. Граф Corrective RAG

```
START → rewrite → retrieve → grade ─┬─ relevant ≥ MIN_RELEVANT → check ─┬─ всё найдено ──► generate → END
                     ▲              │                                  └─ части нет ─┐
                     │              ├─ мало, retries < MAX_RETRIES ─────────► broaden ─┤
                     └──────────────┼──────────────────────────────────────────────────┘
                                    └─ лимит исчерпан ───────────────────────────► generate
```

**Состояние** (`graph/state.py`): `question`, `queries` (запросы текущей итерации), `rewritten` (RU/EN‑переформулировки, их видит грейдер), `missing` (часть вопроса, на которую найденные факты не отвечают, — от `check` для `broaden`), `candidates` (найдено в этой итерации, ещё не оценено), `relevant` (оценено как релевантное, накапливается между циклами), `rejected` (отклонено грейдером — запас для ответа с низкой уверенностью), `seen_ids` (уже оценённые чанки — повторно не оцениваются), `retries`, `answer`, `sources`, `low_confidence`, `steps` (трасса выполнения, редьюсер `operator.add`).

| Узел | Что делает |
|---|---|
| `rewrite` | LLM возвращает JSON `{"ru": …, "en": …}` — поисковые запросы на двух языках. Исходный вопрос тоже остаётся в `queries`: маленькая модель может исказить точный идентификатор. Невалидный ответ → ищем только по исходному вопросу. Переформулировка, где внутри одного слова смешаны кириллица и латиница («Dымчатый кварц» — испорченная транслитерация), отбрасывается: она ничего не находит в BM25 и путает грейдер. |
| `retrieve` | Гибридный поиск (BM25 + вектор → RRF) по каждому запросу; списки разных запросов объединяются ещё раз по reciprocal rank. Уже оценённые чанки исключаются, поэтому поиск идёт на глубину `RETRIEVE_K` + число оценённых — повтор всегда приносит новые чанки. Для каждого чанка запоминается лучший ранг в списке BM25 и в векторном списке по всем запросам. |
| `grade` | LLM оценивает **каждый** чанк отдельно. Видит исходный вопрос **и** его RU/EN‑переформулировки: маленькая модель сама не сопоставит русский вопрос с английским ключом YAML. Сначала цитирует из фрагмента слова, отвечающие на вопрос, потом выносит вердикт: `{"quote": …, "relevant": "yes"/"no"}`. Решает только поле `relevant` (JSON → поле `relevant` в сломанном JSON → yes/no в тексте без JSON → «no»). Цитата сохраняется, если она действительно есть в чанке. Запросы идут параллельно (`GRADE_CONCURRENCY`), текст чанка обрезается до `GRADE_MAX_CHARS`. Отклонённые чанки попадают в `rejected`. |
| `check` | Проверка полноты (`COMPLETENESS_CHECK`): LLM получает текст принятых чанков, делит вопрос на части и для каждой копирует из фрагментов слова‑ответ или `none`: `{"parts": [{"part": …, "answer": …}]}`. Часть считается найденной, только если её цитата действительно есть во фрагментах (сравнение по словам, как у цитаты грейдера). Ненайденные части уходят в `missing`, и граф идёт в `broaden`. Нужна потому, что `MIN_RELEVANT` считает фрагменты, а не ответ: на «при какой температуре печатать и сушить» два фрагмента про сушку останавливали поиск, а модель выдумывала температуру печати. Проверке нужен полный текст чанков: по одной цитате грейдера она объявляла недостающими части, ответ на которые был в остальном тексте чанка. Неразобранный ответ означает «всё найдено» — сломанная проверка не должна стоить лишнего раунда. Пропускается, если повторов не осталось. |
| `broaden` | LLM предлагает до 3 более широких запросов (синонимы, общие термины, идентификаторы, другой язык). Модель видит, какие фрагменты были найдены и отклонены (файл, раздел, начало текста), чтобы уйти от их тем, и чего не хватает по мнению `check` — тогда запросы нацелены на эту часть. Ответ — `{"ru": [...], "en": [...]}`, запросы берутся поочерёдно из двух списков: документ на другом языке находится только запросом на его языке (без этого на «температура печати „Дымчатого кварца“» модель давала три русских запроса и не находила английский `filaments.json`). Запросы со смешанными алфавитами отбрасываются, как в `rewrite`. Все запросы, опробованные с начала (`tried`), показываются модели и отбрасываются, если она их повторит. `retries += 1`. |
| `generate` | Ответ строго по контексту (до `MAX_CONTEXT_CHARS`), на языке вопроса, со ссылками `[n]` на пронумерованные фрагменты; `sources` — файл, строки, раздел для каждого `n`. Если релевантных чанков нет, берутся до 3 отклонённых чанков, которые оба поиска поставили в топ‑`FALLBACK_MAX_RANK` (грейдер мог ошибиться): ответ получает пометку и `low_confidence: true`. Если нет и таких — фиксированное «в базе знаний не найдено», без вызова LLM. К каждому фрагменту контекста добавляются соседние чанки того же файла (`chunk_index ± CONTEXT_NEIGHBORS`, id чанка выводится из файла и номера), пока позволяет бюджет; оценённые чанки в приоритете, соседи ставятся рядом в порядке файла и помечаются в `sources` как `adjacent`. Так в ответ попадает «Root cause» рядом с принятым грейдером «What happened». Промпт требует при неполном контексте назвать, какой части ответа нет, а не подставлять соседнее значение. После генерации ссылки `[n]` на несуществующие фрагменты удаляются; ответ из одних ссылок (например, «[2]») заменяется сообщением и проверенными цитатами грейдера. |

**Маршрут после `grade`** (`Nodes.route_after_grade`): релевантных ≥ `MIN_RELEVANT` → `check` (если ещё есть повторы, иначе сразу `generate`); после `check` (`Nodes.route_after_check`): всё найдено → `generate`, части нет → `broaden`; иначе, если `retries < MAX_RETRIES` → `broaden` → `retrieve`; иначе → `generate` с тем, что нашлось.

**LLM.** Граф зависит только от `BaseChatModel` (`llm.py`): `ChatOllama` или `ChatOpenAI` (любой OpenAI‑совместимый сервер). Для Ollama узлы rewrite/grade/broaden используют отдельный экземпляр с `format="json"` (JSON‑режим), generate — обычный. У OpenAI‑совместимых серверов JSON‑режим поддерживается неодинаково, поэтому там одна модель, а надёжность обеспечивает разбор ответа. Промпты (`graph/prompts.py`) — на английском: маленькие модели лучше следуют английским инструкциям.

Модели с рассуждениями (qwen3) тратят на оценку одного чанка ~200 токенов размышлений вместо ~10 токенов ответа. Поэтому по умолчанию выбрана модель без режима рассуждений — Qwen3‑4B‑Instruct‑2507. Для гибридной qwen3 в LM Studio `LLM_PROMPT_SUFFIX=/no_think` добавляет переключатель к каждому запросу; блоки `<think>…</think>`, если сервер отдаёт их в тексте ответа, вырезаются перед разбором. Тег Ollama `qwen3:4b` (Thinking‑2507) не подходит: `/no_think` Ollama игнорирует, а с API‑параметром `think: false` модель пишет рассуждения прямо в ответ.

**Качество.** Тесты графа проверяют маршрутизацию, а не решения LLM: mock‑грейдер знает правильный ответ. Качество модели измеряет `eval/run_eval.py` — 13 фактов из `eval/facts.yaml` через настоящий MCP по HTTP, отдельно для поиска, грейдера и ответа (см. README, «Замер качества»).

**Тестируемость.** `build_graph(llm, search, settings, json_llm=None)` принимает модель и функцию поиска `(query, k) -> list[Document]`. В тестах — `ScriptedChatModel`: mock LLM, ответ которого зависит от промпта, а не от порядка вызовов (детерминированно при параллельной оценке), и поиск‑заглушка.

## 7. MCP‑инструменты

| Инструмент | Вход | Выход | Ошибки |
|---|---|---|---|
| `index_folder` | `path`, `glob="**/*"` | задача индексации: отчёт (файлов, чанков, пропущено, время), если успела за `INDEX_WAIT_S`, иначе `running` + прогресс | путь не существует / не папка; нет подходящих файлов; индексация уже идёт |
| `ask_question` | `question` | `answer`, `sources[]`, `retries`, `relevant_chunks`, `low_confidence`, `steps[]` | пустой индекс; LLM недоступна / модель не найдена |
| `find_relevant_docs` | `query`, `top_k=5` | список чанков: текст, `source`, строки, раздел, RRF‑score, ранги в BM25 и векторном списке | пустой индекс; `top_k` вне диапазона |
| `index_status` | — | файлы, чанки, `last_indexed_at`, модель эмбеддингов, статус LLM | — |

Описания инструментов и `instructions` сервера говорят, что это **внутренняя база знаний** по теме `KB_TOPIC` (по умолчанию — 3D‑печать: принтеры, прошивки, Klipper, электроника, мастерская) с непубличными фактами, и что её нужно использовать раньше общих знаний — от этого зависит, выберет ли хост‑агент инструмент без подсказки. Тема вынесена в конфиг: при смене корпуса меняются и описания.

- `ask_question` проверяет LLM перед запуском графа (понятная ошибка с адресом и моделью) и шлёт **progress‑уведомления** после каждого узла графа: клиент видит ход работы, а клиенты с «reset timeout on progress» (MCP Inspector) не обрывают долгий вызов.
- `index_status` дополнительно показывает доступность LLM (`reachable`, `model_available`).
- Все ошибки входа и окружения возвращаются как `ToolError` с текстом, понятным агенту.

**Прокси.** Python‑клиенты (httpx) учитывают системный прокси, в том числе на Windows из реестра. При локальном запуске с включённым прокси/VPN запросы к `localhost` (Ollama, сам MCP‑сервер) могут уйти в прокси и получить 503 — нужен `NO_PROXY=localhost,127.0.0.1`. В Docker это не проявляется.
